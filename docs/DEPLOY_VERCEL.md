# Deploying to Vercel

Kamplug is a standard Next.js 16 app with no server secrets, database or API keys. All data lives in
each visitor's browser. Deploying is import and click.

## 1. Before you deploy

Run the same checks CI would:

```bash
pnpm install --frozen-lockfile
pnpm check            # typecheck + lint + unit tests
pnpm build            # must finish with no errors or warnings
pnpm test:e2e         # optional locally; needs the build above
```

## 2. Import the project

1. In Vercel, **Add New → Project** and import this repository.
2. Leave the detected settings alone:
   - Framework preset: **Next.js**
   - Install command: `pnpm install` (Vercel reads `packageManager` from `package.json`)
   - Build command: `next build`
   - Output: default
   - Node.js version: 20.x or 22.x (the project requires ≥ 20.9)
3. Click **Deploy**.

## 3. Environment variables

None are required to deploy: without them the app runs with each browser keeping its own data.
To switch on the shared backend (Neon, Google sign-in, Cloudflare R2), add the variables listed in
the README under [The backend](../README.md#the-backend). Other optional ones:

| Variable                   | When to set it                                                                                                                                                                  |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NEXT_PUBLIC_SITE_URL`     | When you add a custom domain, e.g. `https://kiosk.ng`. Otherwise canonical URLs, the sitemap and OG images use `VERCEL_PROJECT_PRODUCTION_URL`, which Vercel sets automatically |
| `NEXT_PUBLIC_MOCK_LATENCY` | Upper bound in ms of simulated network delay in the browser-only data layer. Default `900`; `0` turns it off                                                                    |
| `NEXT_PUBLIC_DATA_SOURCE`  | Only to override: it's `remote` when `DATABASE_URL` is set and `mock` otherwise                                                                                                 |

`NEXT_PUBLIC_*` values are inlined at build time, so **redeploy after changing them**.

## 4. After the first deploy: checklist

- [ ] `/` loads the landing page; **Create your account** signs you up and lands on `/home`.
- [ ] Open a shop from the rail's **+** (or `/open-shop`) and add a product.
- [ ] In a second browser (or a private window), sign up as someone else, find the product and
      place an order paying at pickup. Back in the first browser the order shows under
      **Orders** in Shop Studio; move it through to completed. (Without a backend each browser
      has its own data, so do both steps in the same browser by signing out in between.)
- [ ] `/robots.txt` and `/sitemap.xml` show your production domain, not `localhost`.
- [ ] `/opengraph-image` renders the share card; paste the URL into a link-preview checker.
- [ ] `/manifest.webmanifest` loads; Chrome DevTools → Application shows the manifest and an
      active service worker (`/sw.js`).
- [ ] Turn on DevTools offline mode, reload a visited page (it still works), then open an unvisited
      one (the **You're offline** page shows).
- [ ] An unknown URL shows the custom 404.
- [ ] Response headers include `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy` and
      `Permissions-Policy`.
- [ ] Run Lighthouse (mobile) on `/` and `/explore` against the deployed URL.

## 5. How it runs on Vercel

- Most routes are prerendered static shells (`○`/`◐` in the build output) served from the CDN.
  `/explore` and `/search` render per request so the heading and filters arrive in the HTML.
- Icons, the OG image, `robots.txt`, `sitemap.xml` and the manifest are generated by metadata
  routes at build time.
- `/sw.js` is served with `no-cache` so a new deploy's service worker is picked up on the next
  visit. To force every client to drop its cached pages, bump `VERSION` in `public/sw.js`.
- Preview deployments use the same database as production unless you give the Preview
  environment its own `DATABASE_URL` (a Neon branch works well for that).

## 6. Connecting the backend

The backend is built. Follow [The backend](../README.md#the-backend) in the README: add the
variables, register the Google redirect URI, make the R2 bucket public, redeploy. Then switch on
the remaining features in `src/config/features.ts` (online payments, password reset email,
payouts) as each one becomes real; search for `BACKEND-SEAM`.
